## 结论

本项目的核心问题是**会话数据源**。剪贴板只是 PC 窗口路径中已验证的手工取数方式，不能代表完整的会话读取方案。

建议先确认企业是否能够并愿意使用企业微信官方的**会话内容存档**能力。官方开发文档提供“获取会话内容”入口（[企业微信开发文档：获取会话内容](https://developer.work.weixin.qq.com/document/path/91774)）。如果管理员确认企业的存档功能、员工范围、外部联系人授权/告知、数据范围和合规条件满足需求，优先评估以官方 SDK/API 作为消息采集源；这是与“从当前 PC 窗口视觉读取”不同的数据路径，也可能要求把采集服务放到受控 Agent/后端。当前项目尚未确认企业是否已开通、适用范围、费用/授权条件、数据保留和 SDK 集成要求；本轮未接入该接口。

若官方存档不适用，再评估 PC 窗口读取。现有 UIA 没有暴露足够的聊天语义；截图/OCR最多能从当前可见区域提取候选文本，剪贴板则依赖用户选择。它们都不能单独保证自动定位正确会话、读取完整历史或给每条消息提供稳定身份。因此在此路径下，短期安全方案仍是用户手动打开会话、手动选择/复制，AutoIM 解析并明确提示“可见/复制范围不等于完整会话”。

自动发送目前没有实现，也没有足够的唯一会话身份、消息方向和结果校验依据；仍保持未验证。以上判断基于仓库代码、用户提供的 Windows 实测，以及公开可访问资料；官方 API 页面在本次检索工具中无法直接读取，具体开通与接口条件必须由企业管理员通过官方开发者中心核实。

## 可行性分项

### 0. 官方会话内容存档：应先确认是否可用

官方开发中心有“获取会话内容”入口：[企业微信开发文档：获取会话内容](https://developer.work.weixin.qq.com/document/path/91774)。这表明项目应先让企业管理员核实官方存档是否覆盖所需的员工与客户会话、授权与告知要求、消息/媒体范围、数据保留和许可条件，再决定后续技术路线。

该路径不等于在 Windows PC 上读取当前屏幕。若适用，采集通常应作为独立、受控的数据接入组件评估，处理官方凭证/密钥、授权变化、消息游标/去重、解密和敏感数据保护；PC Agent 可继续负责本机 GUI 或人工接管。当前未验证企业是否具备存档许可和所需授权，因此这只是**优先核实项**，不是已经选定或实施的架构。

本轮网页工具未能读取官方开发文档正文，故没有把第三方文档镜像中的保留期限、接口限制或授权细节写成确定结论。管理员应以其企业后台和当前官方文档为准。

### 1. 会话定位：当前低可行，须先取得独立身份依据

窗口标题和 HWND 只能锁定企业微信主窗口，不能绑定具体会话。手工核对标题属于人机协作证据，但相同显示姓名、标题装饰或会话切换都可能造成误认。公开的 Windows UI Automation 资料说明，应用控件通过 provider 暴露给 UIA；自定义控件缺少 provider 时，客户端可能只能获得窗口句柄等基础信息。[Microsoft UI Automation Providers Overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview)

这与本项目现有 UIA 扫描结果相符，但不证明企业微信所有版本、所有页面始终不可访问。当前处理建议：继续要求用户手动打开目标会话；如果标题无法唯一核对或发生会话切换，记录为 `UNKNOWN` 并停止后续动作。不要以姓名、公司名、标题截图相似度或窗口句柄代替会话 ID。

### 2. 自动多选：技术上可试验，当前不能启用真实输入

现有事实只验证了用户使用企业微信原生能力多选复制三条消息。AutoIM 的现有坐标路线要求新鲜截图、窗口 PID/HWND/Rectangle 一致、聊天区域标定和前台检查，但真实输入安全闩仍关闭。坐标路线还需要适配滚动、窗口尺寸/DPI、菜单状态和消息高度变化。

因此可行性探索的最小边界应是先形成操作状态图与可观测证据清单，不向企业微信注入按键或鼠标操作。后续若进入真实 PoC，须单独授权、重新验收标定，并先覆盖无客户资料的测试会话；任何目标歧义都应取消操作。

### 3. 复制完整性：只能做校验信号，不能推断“全部消息”

当前解析器可以统计识别出的消息、保留顺序并暴露未识别文本和边界歧义。它不知道用户原本选中了几条、当前视口是否还存在未复制消息，也没有企业微信提供的选择计数或消息唯一 ID。

Windows 官方资料说明 `GetClipboardSequenceNumber` 可用于判断剪贴板内容是否变化；该值本身不提供复制来源或选区范围。[Microsoft: Using the Clipboard](https://learn.microsoft.com/en-us/windows/win32/dataxchg/using-the-clipboard#query-the-clipboard-sequence-number)

可用作后续提示的信号包括：本次复制前后 sequence number、原始剪贴板格式、解析出的消息条数、消息边界警告、用户声称的选择条数（若界面确有可核验计数）。这些信号只有在来源关联和预期条数都可独立确认时，才可能组成完整性校验；缺少任一依据时结果只能是“完整性未知”，不能标记为完整。

### 4. 安全发送：当前不可行

路由发送前至少缺少：唯一会话绑定、联系人身份、消息方向、本机账号身份、发送目标的二次核对、发送后结果确认与重复发送保护。现有 Driver 没有统一发送接口，项目原则要求 AI 与人工共用统一 `send_message()` 通道。

发送应作为独立阶段最后评估。设计必须支持预览、明确确认、会话状态复核、单次发送及可观测结果；遇到焦点变化、窗口身份变化、会话身份不确定或结果不明时停止，不能自动重试。

## 后续阶段建议

本次只完成研究，不改 Driver、GUI 或真实输入安全闩。建议以后按以下门槛推进：

1. **会话证据研究**：整理当前会话标题、同名联系人、企业标签和切换状态的真实可观察证据；无法建立唯一绑定时，范围保持用户手动打开会话。
2. **多选操作方案评审**：先在测试账号上由用户观察并记录原生多选的进入、追加、退出、滚动和取消行为。确认可检测状态及安全停止条件后，才决定是否单独授权 Dry Run / 真机 PoC。
3. **完整性信号试验**：使用固定、无敏感的测试消息，比较人工预期条数、实际复制文本条数、复制格式和重复/边界情况。未建立可靠预期条数来源前，功能名称与状态只能称“解析结果”，不能称“完整记录”。
4. **发送阶段单独立项**：先完成会话身份、方向、统一发送 API、人工确认、结果验证和幂等策略评审；本研究不授权进入发送开发。

**决策建议：**先由企业管理员确认官方会话内容存档能力及授权范围；若适用，单独评估官方接口采集。若不适用，再决定 PC 窗口路线是否只支持用户手动打开会话后读取屏幕当前可见/用户复制的内容，并在产品里明确这不代表完整会话。下一段可选 PoC 仅应在独立授权后评估用户辅助选择；自动发送继续留在后续阶段。
